# Dart data modelling — the construct ledger

> **Sources.** Language and Effective Dart prose: `dart-lang/site-www` @ `fccd24a0` (2026-06-20),
> read from the local `ai-context` store. API facts: the **pinned** toolchain only —
> Flutter 3.44.8 / Dart 3.12.2 per `.fvmrc` — *not* whatever `dart.dev` calls stable, because the
> store tracks default branches and can run ahead of what this project builds against.
> Compiled 2026-08-07.

**Why this file exists.** `planning/architecture.md` was written without applying the Dart/Flutter
canon to it, and prescribed offset tables "as data (YAML/JSON), not code" — a config-file instinct
in a language whose libraries have no asset system. Fixing that raised the general question this
file answers: *which Dart construct is right for each modelling decision this project makes?*

**The standard this file is held to** is the one `java-semantics-notes.md` already sets:

> an entry's Dart-side claim must rest on a citation (Dart API docs / the language spec), not on
> model memory — *a signature is not a mechanism; neither is a remembered default*.

That protocol earned its keep on the first pass. Two confident recollections were wrong:
`UnmodifiableUint8ListView` turned out to be **absent** from the pinned SDK, and class modifiers
turned out **not to apply to `enum`** at all. Every claim below carries a source; anything without
one is labelled **[judgement]** and is this project's opinion, not a language fact.

---

## 1. Binary format layout tables → **enhanced enums**

Each field becomes a *value* carrying its own offset and width, behind a shared interface.

```dart
enum GamNpcField implements FormatField {
  creOffset(0x04, 4),
  creResref(0x0c, 8),
  name(0xc0, 32),
  voiceSet(0x158, 8);

  const GamNpcField(this.offset, this.length);
  @override final int offset;
  @override final int length;

  static const int structSize = 352;
}
```

| Fact | Source |
|---|---|
| Enhanced enums may declare fields, methods and const constructors, and **may implement an interface** (`enum Vehicle implements Comparable<Vehicle>`) | `language/enums.md:44-98` |
| Requires language ≥ 2.17 | `language/enums.md:100-102` |
| Instance variables must be `final`; all generative constructors must be `const`; there must be at least one value | `language/enums.md:54-65` |
| `values` is generated automatically and **a member named `values` cannot be declared** | `language/enums.md:61-62` |
| `.name` gives the identifier as a string, free | `language/enums.md:155-162` |
| `index`, `hashCode` and `==` **cannot be overridden** | `language/enums.md:60` |
| Enums are implicitly **sealed** and automatically extend `Enum` | `language/enums.md:17-26` |
| Class modifiers **do not apply to `enum`** — so `sealed enum` / `final enum` are not valid | `language/class-modifiers.md:35-37` |

⚠️ **`.name` cannot satisfy an interface. Found by compiling, 2026-08-07.** An interface declaring
`String get name` looks like it should be free for enums — it is not, and
`enum X implements ThatInterface` fails with *"Missing concrete implementation of
'getter …name'"*. `dart:core` declares it as `extension EnumName on Enum`, and the SDK states the
reason in place (`lib/core/enum.dart:134-137`): it is an extension *"instead of an instance method
in order to allow enum values to have the name `name`"*. So `.name` works when the static type is
the enum, but discharges no interface obligation.

**[judgement]** Consequence adopted here: `FormatField` declares only `offset` and `length`, and
diagnostics use `toString()` — which for an enum yields `GamHeaderField.partyGold`, a better label
than the bare identifier anyway.

**Why this over a class of `static const int`** *(the shape rejected in D6)* **[judgement]:** because
`values` is iterable, the table's own consistency becomes a *test* rather than a review item — no
overlapping fields, everything inside `structSize`, and the last field ending exactly at
`structSize`. That last assertion is precisely the fact whose absence produced the stride bug
(`docs/findings/verified-format-offsets.md` §Known bugs). It also serves *preserve unknown bytes*:
known ranges are enumerable, so unknown regions are computed as their complement instead of tracked
by hand.

**Prior art that disagrees, and why it does not transfer.** `google/protobuf.dart` — the closest
production Dart binary codec — uses exactly the rejected shape: `PbFieldType` is `static const int`
bitmask constants (`protobuf/lib/src/protobuf/field_type.dart`), with
`// ignore_for_file: constant_identifier_names`. Three differences **[judgement]**: their field
types are **composable bit flags** (`REQUIRED_BIT | REPEATED_BIT | …`) and enum values cannot be
bitwise-OR'd; their descriptors are **generated by protoc**, so human readability is secondary; and
the code predates enhanced enums by roughly a decade. GAM/CRE offsets compose with nothing, are
hand-transcribed from IESDP by a human comparing against a spec, and need iteration for the
invariant test.

## 2. Version dispatch (D3) → **sealed classes + exhaustive `switch`**

> Exhaustiveness checking "reports a **compile-time error** if it's possible for a value to enter a
> switch but not match any of the cases." Enums and sealed types "are particularly useful for
> switches because, even without a default case, their possible values are known and fully
> enumerable." — `language/branches.md:207-232`

Class modifiers require language ≥ 3.0 (`language/class-modifiers.md:15-18`).

### Resolved by compiling, 2026-08-07 — the docs are stale, the behaviour is stronger

`language/enums.md:138-153` shows a switch *statement* missing an enum case producing a **WARNING**,
which contradicts `branches.md:209-211`. Compiled against the pinned SDK, **all four combinations
are errors**:

| Construct | Diagnostic |
|---|---|
| `switch` **statement** over an enum, missing a value | `error … non_exhaustive_switch_statement` |
| `switch` **expression** over an enum, missing a value | `error … non_exhaustive_switch_expression` |
| `switch` **statement** over a `sealed` type, missing a subtype | `error … non_exhaustive_switch_statement` |
| `switch` **expression** over a `sealed` type, missing a subtype | `error … non_exhaustive_switch_expression` |

So `enums.md`'s "warning" text is **out of date**; statements get the same compile-time protection
as expressions. Adding a `GamV22` codec without handling it anywhere will fail the build, which is
exactly what D3's pluggable dispatch wants. **[judgement]** Prefer switch *expressions* anyway, for
the usual reason — they are values, so there is no fall-through path to forget.

## 3. Retaining original bytes → **`asUnmodifiableView()`**

This is the construct the project's hardest rule depends on — *preserve unknown bytes* rests on a
buffer that must not be mutated.

| Fact | Source |
|---|---|
| `Uint8List.asUnmodifiableView()` and `ByteData.asUnmodifiableView()` exist, documented as *"A read-only view of this [Uint8List]"*, annotated `@Since("3.3")` | pinned SDK `lib/typed_data/typed_data.dart:951-953`, `:521` |
| **`UnmodifiableUint8ListView` does not exist in the pinned SDK** — removed, not merely deprecated | same file, no match |
| Naming rationale: *"PREFER naming a method `as___()` if it returns a different representation backed by the original object"* | `effective-dart/design.md:368` |

**It is a view, not a copy**, so retaining a 96 KB save costs nothing and mutation attempts throw.
**[judgement]** This makes "never regenerate a file from the model alone" enforceable by the type
system rather than by discipline.

Prior art: `google/protobuf.dart`'s `UnknownFieldSet` solves the same *principle* — capture what you
do not understand and re-emit it verbatim. The mechanism differs **[judgement]**: protobuf's wire
format is self-describing so it enumerates unknown *fields*; GAM/CRE are fixed-layout so unknowns
are byte *ranges*, which is why the enumerate-known-and-take-the-complement approach works here.

## 4. Multi-value returns → **records**; domain models → **classes**

| Fact | Source |
|---|---|
| Records are anonymous, **immutable**, aggregate, fixed-size, heterogeneous, typed. Fields have getters, no setters. Language ≥ 3.0 | `language/records.md:12-22,104-107` |
| Named field *names* are part of the type; **positional field names are documentation only and do not affect the type** | `language/records.md:72-95` |
| Equality is **structural** — same shape, same field values | `language/records.md:155-160` |

⚠️ **The hazard, straight from the docs' own example** (`records.md:164-167`):
`(int x, int y, int z) point = (1, 2, 3)` and `(int r, int g, int b) color = (1, 2, 3)` are the
**same type** and compare **equal**. **[judgement]** So records are right for *local* multi-value
returns and wrong for domain concepts that need distinct identities — a `(int offset, int length)`
and a `(int count, int size)` are indistinguishable to the type system. Domain models stay classes.

## 5. Edit commands → **sealed hierarchies + switch expressions**

Same mechanism as §2: a `sealed` supertype makes exhaustiveness a compile-time error, so adding a
command without handling it fails to build. `branches.md:234-259` gives the shape and calls it
"a somewhat functional algebraic datatype style".

## 6. Errors → **`Exception`, never `Error`**

> "**DO throw objects that implement `Error` only for programmatic errors.**" —
> `effective-dart/usage.md:1561`

**[judgement]** Malformed save data is not a programmer mistake — it is expected input to a tool
whose whole job is reading other people's files. So codec failures are Exceptions.

The project's choice (D-record pending, see `planning/architecture.md`) is
`InfinityFormatException implements FormatException`: catchable as the core type, but precise
enough for the repository layer to catch *this library's* failures alone. Named constructors per
failure mode follow `google/protobuf.dart`'s `InvalidProtocolBufferException`, which uses
`.invalidTag()`, `.invalidWireType()`, `.malformedVarint()`, `.truncatedMessage()`
(`protobuf/lib/src/protobuf/exceptions.dart:13-40`).

Related: *"AVOID catches without `on` clauses"* (`usage.md:1530`), *"DON'T discard errors from
catches without `on` clauses"* (`:1554`), *"DO use `rethrow`"* (`:1586`).

## 7. Concurrency → **`Isolate.run` in the package, `compute` only in the app**

> "If you're using Flutter, you can use Flutter's `compute` function instead of `Isolate.run()`." —
> `language/isolates.md:59-64`

| Fact | Source |
|---|---|
| `Isolate.run<R>(FutureOr<R> computation(), {String? debugName})` — spawns, runs, captures the result, terminates, and rethrows errors on the main isolate | pinned SDK `lib/isolate/isolate.dart:253`; `language/isolates.md:47-55` |
| `dart:isolate` is a core library, available to pure Dart | pinned SDK `libraries.json:88` |
| `compute<M, R>` is declared in `flutter/lib/src/foundation/isolates.dart:81` and exported from `package:flutter/foundation.dart:40` | pinned Flutter package |

**This is not a preference.** `packages/infinity_formats` may never import `package:flutter`, so
`compute` is unreachable there *by contract* — enforced by `test/flutter_free_test.dart`. Any
isolate work inside the format package uses `Isolate.run`.

## 8. Extension types → **not yet. [judgement]**

Tempting for typed offsets (`extension type ByteOffset(int _)`), and genuinely novel. Two reasons
to decline for v1:

> "Extension types are a compile-time wrapping construct. At run time, there is absolutely no trace
> of the extension type. … This makes extension types an ***unsafe* abstraction**, because you can
> always find out the representation type at run time and access the underlying object."
> — `language/extension-types.md:430-436`

The docs show the escape hatch themselves: `myUnsafeId = safeId as int; // OK` (`:46`).

And **they would not have caught the bug they look useful for.** The stride bug was
`(invOff - partyOff) ~/ partyCnt`. Under extension types that is still
`ByteOffset - ByteOffset → int ~/ Count`, which type-checks fine. What prevents it is not doing
arithmetic at all — reading the documented `structSize`. Adopting a construct the language docs
call *unsafe*, in a project whose failure mode is silent save corruption, needs a stronger argument
than novelty.

Revisit if a concrete confusion appears that this would actually prevent.
